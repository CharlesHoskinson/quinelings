# QDL v1 work plan — Living Thoughts

The user requested production QDL v1 for agent thoughts, updated APIs and standard library, a better ranch, ten technical specialists and five branding/marketing specialists. This plan records active work; it is not a stable release declaration.

## Research and convergence

Ten technical workstreams cover public Midnight.city task context, language semantics, runtime/API, standard library, security, compatibility, formal methods, ranch lifecycle, graphics and acceptance evaluation. Five additional specialists cover positioning, website copy, developer messaging, launch narrative and voice/claim review. The tagline is **Living Thoughts**. Three workers can run alongside root; queued assignments will receive distinct agent tasks as slots become available. Execution evidence lives in `research/qdl-v1/execution.json`.

Scrapling retrieves public City material with bounded requests and provenance. Publicly reported plans, observations and confirmed results must remain distinct; inferred task classes are labeled. Public context does not grant access to private agent reasoning or authority to act in the City.

## Production candidate obligations

The candidate must define closed syntax, exact semantics, standard operation signatures, runtime inputs, explicit effects, resource ceilings, stable source identity, diagnostics, recovery and compatibility. Existing source/genomes must remain readable without silently rewriting historical identity. A v1 marker alone cannot establish stability. A release needs concrete migration rules, conformance fixtures, independent expected outcomes, transport/schema agreement and packaged-consumer verification.

Agent-facing requirements include reusable typed programs over supplied observations, structured decisions and plans, source-bound run evidence, explicit unavailable/uncertain outcomes, and complete constructor-source reproduction. Model-generated text remains a proposal until the same deterministic compiler validates its plan. New external host integrations require explicit authority and separately testable acknowledgements; no program contains credentials or arbitrary host code.

Ranch improvements should make collaboration useful and legible: distinguish meetings, construction proposals, admitted offspring, execution and recorded outcomes. Source reproduction, social history and persisted session evidence have separate meanings. Graphics changes must be reviewed on actual desktop/mobile scenes and measured honestly; CPU submission is not presented-frame performance.

## Integration sequence

1. Retrieve public task evidence and complete the fifteen specialist reports.
2. Converge a concrete candidate and acceptance matrix; resolve conflicting recommendations against actual code and experiments.
3. Implement the language/standard library, API/adapters and ranch changes in assigned files.
4. Extend appropriate Lean/Quint models and executable conformance/security/compatibility checks.
5. Apply the Living Thoughts copy to the website and developer documentation.
6. Test the installed package, actual browser and publication artifacts; integrate to main and publish GitHub Pages.

Release status will be reported against the gates. Unsupported features and unproved model/runtime correspondence will not be described as completed production guarantees.
