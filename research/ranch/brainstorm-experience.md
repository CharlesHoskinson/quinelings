# Ranch experience: a meadow with an inspectable nursery

Proposal for ten-workstream convergence, 2026-10-04. This report owns no runtime changes, makes no claim of completed ranch verification, and does not authorize deployment. Read `AGENTS.md`, `docs/RANCH-WORKPLAN.md`, `create.html`, `creation.js`, `creation.css`, `docs/PROGRAM-CONTRACT.md`, and the first semantics/genetics/social proposals. The existing creation workspace is the interaction foundation: source-authored bodies, clause-to-operation inspection, explicit Run, separate recorded results, and exact-source exports.

## Recommended page and first impression

Add a dedicated `ranch.html` linked beside Create and Collection. Keep creation focused on authoring one program. Ranch starts with ten identifiable residents distributed across four spacious clearings, a mixture of small conversations and solitary forms. Residents are the actual admitted source-backed programs, not generic particles or ornamental silhouettes masquerading as executable organisms. Start with a still, fully composed scene and a conspicuous **Start social simulation** button. Visitors can inspect immediately. A short opt-in demonstration can show them hanging out; autonomous task execution must never be the price of seeing the scene come alive.

Use the current deep blue ground, mint controls and operation-role colors. Add subtle clearing contours and diffuse pools of light, preserving enough contrast around every body. Avoid fences, dashboards of counters, decorative science gauges and hovering speech bubbles over every resident. Maintain open space and stable framing; group arrangement, body silhouettes and restrained connecting ribbons communicate social behavior. Source-selected pigments remain semantic. Warm clearing light is an external social overlay, never a substitute for the program's chromamapping.

Desktop hierarchy:

1. A compact introduction: **A ranch for useful little programs.** Supporting sentence: **Let them meet. Inspect what a child would inherit. Run its task when you choose.** Persistent qualifier: **Experimental · local simulation**.
2. A meadow occupying roughly two thirds of the first screen, with a resident/inspector column beside it. Selected names stay visible; body detail expands in the inspector rather than enlarging overlapping residents.
3. A nursery immediately below, showing inert candidates and admitted offspring, followed by a bounded activity list. Pairing completion reveals a nursery item without moving focus or jumping the page.
4. Explanation and recovery details remain available below the primary interaction. An empty nursery explains the next action rather than displaying a blank grid.

A selected resident has a mint outline, a fixed name label and a matching list-row state. Pair partners gain two distinct slot markers and a thin linking ribbon; the ribbon is decoration. Gathering members use small clearing labels. Never rely on color, proximity or motion to distinguish these states.

## Three visible layers of control

| Layer | Controls | Required explanation and behavior |
| --- | --- | --- |
| View | Body / Program / Recorded result; Watch gestures; static phase scrubber | Changes presentation only. Does not tick the world, create pairings or run tasks. |
| Social world | Start/Pause social simulation; Step one tick; restart with seed in details | Changes movement/invitation state. Creates pairing proposals, never executable children or task records. Hidden tabs pause; return paused with a clear Resume action. |
| Program | Prepare offspring; Add to ranch; Run task; Create verified copy | Each action names its concrete consequence. No run occurs during preparation or admission. Verified copy retains the current fresh-execution semantics and discloses that fact. |

Keep world tick, world state and selected resident's last run separate in a compact status strip: **Social simulation paused · tick 240** and **Selected task: not run here**. Do not use a single Play button, “alive” status, fertility meter or “energy” display that confuses clocks or invents resource semantics. The seed is a deterministic scenario setting, not a hidden randomization switch. Changing it requires a deliberate restart; inspection never restarts the world.

The gesture toggle starts off and pauses independently. If social simulation continues while gestures are off, resident positions can still change; describe both switches. Add an obvious **Pause all motion** view action that pauses the world and gesture clock. Under reduced motion start both paused and use discrete steps if desired; state inspection remains complete without animation.

## Onboarding and social choreography

Use a small dismissible three-step guide within the page, with no modal or autoplay:

- **Meet a resident:** select one to see its thought, actual operations and owned body regions.
- **Let them meet:** start the local social simulation or inspect the deterministic example pairing using **Show example pairing**. The latter loads a labeled scenario through the world command path, not a fabricated success notification or task run.
- **Review a child:** choose a recipe, inspect the candidate, add it, and separately run its task.

For a first deterministic scenario, place an eligible pair close to a free clearing and show their state changes: invitation → reciprocal invitation → approaching → courting → pairing ready. Avoid promising an exact time when reservations or unavailable residents may delay them. A compact selected-pair timeline uses those actual states; it is not a countdown guaranteeing a child. Courtship uses a gentle orientation overlay and clearing warmth; it cannot rewrite source-authored body geometry or alter task meaning. The social proposal's distinct resident IDs, exact parent artifact IDs, creation tick and expiry are inspectable.

Participation is a local scenario policy, labeled **Allow social invitations**, separately adjustable for each resident. It is not human consent or evidence that a typed recipe will work. Structural affinity reads **Shared operation roles** or **Different body structure**, with its actual bounded score available in details. Avoid invented conversation, feelings, intent comprehension and a compatibility percentage that mixes social attraction with compiler checks.

A visitor may select two available residents and choose **Invite this pair**. Dispatch two explicit participant invitation commands and let the same reciprocal protocol and reservations decide the outcome. Do not let a canvas gesture bypass one-sided participation, expiry or slot bounds. A pair ready to inspect does not promise a genetically compatible child.

## Resident inspector: thought → program → body

Reuse the existing creation inspector's accurate linkage and passive controls. The resident name is followed by independent identity labels: resident ID, abbreviated source hash with accessible full value, and derivation status. Two residents may carry exactly the same source; never collapse them into one individual in the scene.

Three connected sections, each accessible without selecting the canvas:

- **Thought:** companion wording and interpretation if present, otherwise **Original thought unavailable in recovered source**. Mechanically generated offspring summaries are explicitly labeled **Generated recipe summary**. Do not present concatenated parent sentences as the child's authored thought.
- **Program:** ordered operations and inputs, declared units when validated companion metadata exists, outputs and simulated-action indicators. Select an operation using a normal button to highlight its owned body territory. Explain that a task kernel's internal items are not extra graph organs.
- **Body:** source-authored assembly and gesture, component ownership, task/body change flags, and the larger portrait with phase scrubber. A Program overlay shows actual dependencies; a social link remains visually and textually distinct from a computation edge.

Recorded result defaults to **No run recorded for this source**. A selected prior source's result is marked stale and cannot color the new child. Reading a lineage record, selecting parents, inspecting regions or recovering bytes makes zero task runs. Keep **Run task** visible and local to the currently selected source; show the exact target name to prevent accidental parent runs.

## Recipe chooser and reviewable nursery

Do not compress different mechanisms into a single “Breed” button. A ready pairing offers these explicit choices, subject to the final admitted semantics:

| User-facing choice | What the review must say |
| --- | --- |
| **Merge tasks** | Which parent outputs are joined or connected, ordered output labels, and whether both complete tasks execute. Parallel report composition does not imply improved capability. |
| **Mate task fragments** | Recipient task, pure donor slice, exact replacement/port, validated structural types and units, and surviving contribution from each parent. No inferred coercion. |
| **Inherit body style** | Which parent's task is retained exactly, which bounded authored traits change, and that no new computational capability is claimed. |
| **Create exact copy** | Complete source stays identical. Existing verified-copy behavior runs a fresh instance and compares it with an available parent run; label the button **Create and run verified copy**. Keep this outside courtship requirements. |

The first three buttons are **Prepare candidate**, not Run or Birth. Candidate building should use one explicit fixed recipe/seed at a time and never search unboundedly for attractive outcomes. An optional bounded alternative requires another deliberate preparation and displays the recipe change. A ready-to-admit candidate card contains:

1. Two ordered parents and recipe, child silhouette, proposed output names and independently computed task/body/source change flags.
2. An inheritance view: child operation rows annotated with parent source and node, newly generated nodes, removed recipient nodes, and changed body traits. Use text rows alongside graphical arrows.
3. Bounds/validation outcomes and explicit unknowns. **Accepted by compiler** does not mean **useful**, **safe in the world**, or **matches all English intent**.
4. Two actions: **Add to ranch** and **Discard candidate**. Before admission say **Candidate · not a resident · not run**. After admission say **New resident · no run recorded**, then offer **Run [child name] task**. Adding must not automatically call the existing `copy()` path.

Running writes a fresh child-specific result and exact-source verification. Fixture evidence can be shown only when an actual explicit run produced it; recipe preparation must not secretly execute parent or child tasks to populate comparison panels. Before a run, show inspectable graph/recipe differences and supplied fixture expectations labeled as expectations. A useful example should use the semantics proposal's donor mean `[10,20,30] L` and recipient budget 5 for 12 L: after deliberate child Run, child allocates 12 and leaves 8. Show the independently recorded parent results only if those parents were explicitly run. Source difference alone never supports a novelty claim.

## Rejections, capacity and lineage

Rejected matches are visible without shaming either resident: **Pairing ready; this task recipe cannot be prepared**. Attach the actual diagnostic to both relevant operation rows, e.g. **Donor returns number<L>; recipient requires number<s>**, **Typed companion metadata unavailable**, **Protected simulated-action guard**, **Source budget exceeded**, or **Parents changed; prepare a fresh candidate**. Preserve current selection and draft recipe. Offer only valid next actions: inspect ports, select a different recipe, supply a validated companion artifact, or dismiss. Never silently downgrade task mating into body-only offspring.

Record a rejection as a bounded attempt event, not an offspring or ancestry edge. One unavailable invitation is a social result, not a genetic rejection. Expired proposals show their reason and remain unavailable for admission. Full nursery/source/lineage/spawn capacity reports the specific exhausted store and its configured limit; no invisible eviction, auto-run or destructive cleanup. Reset/remove controls belong in explicit details with concrete consequences and an undo where the eventual store design permits it.

Nursery cards distinguish prepared candidates, admitted unrun children and children with fresh recorded runs. Show direct parents in a readable two-parent strip and an expandable ancestry list, with missing ancestors as **Source unavailable**. Do not recursively duplicate all ancestors in every card. Multiple derivations of the same source remain selectable. Lineage is asserted or replay-verified provenance according to the final implementation, not authenticated authorship. Recovery of source alone shows **Lineage unavailable** when no companion record was supplied.

Exports reuse Artifact, Source, Wave samples and RGB genome names. Add a clearly separate lineage/recipe export or include it in a versioned companion bundle only after that schema is audited. Explain coverage beside the buttons: **Source carries the executable task, body and gesture. Companion artifacts may carry thought, validated type evidence and lineage.** A screenshot is not a recoverable genome. Imported/recovered children enter still and unrun; parent run records, invitation settings and authority are never inherited.

## Responsive and accessible implementation

On narrow screens use meadow → resident list → inspector → nursery. Keep a 280–360 px tall meadow overview and an expandable larger portrait rather than shrinking the full inspector next to it. Avoid horizontal page scrolling at 320 CSS px; long source hashes and JSON wrap or scroll inside their own labeled containers. Selected-resident controls remain near the selection, without a sticky footer obscuring content or keyboard focus.

Canvas is a visual overview with a concise accessible description. A DOM resident list supplies all names, social states, selection and pairing actions. Give each row a real button and `aria-pressed` selection state. A static text line describes the selected resident's clearing and partner; do not create a constantly changing screen-reader tree of coordinates. Nursery and lineage use semantic lists/headings. Optional arrow-key shortcuts may supplement ordinary Tab/Enter controls; avoid custom grid semantics unless implemented completely.

Use visible focus, labeled controls, text-plus-icons for state, 44 CSS px minimum design targets, and contrast verification against the final palette. Keyboard selection opens an inline inspector without stealing focus. If an intentional modal is introduced later, manage initial focus, Escape and restoration; it is unnecessary for the baseline. After explicit candidate admission, place focus on the new resident heading or Run button only when that transition was user initiated. Simulation events never steal focus.

Announce explicit command success/errors in a polite status region. Keep the full activity list accessible, but do not stream every social tick into `aria-live`. Announce selected-pair readiness once, coalesce bounded notifications, and provide **Announce social events** off by default. Errors are readable text at the responsible control. Reduced motion removes travel decoration, fades and authored loops, retains static connection markers/state labels, and allows discrete simulation stepping. Pause all motion must remain visible for users without an OS preference.

## Implementation sequence and review gates

First separate ranch world state, view state, source/artifact store and run records; use pure reducer commands for world changes. Add the static scene plus DOM resident list and reuse passive renderer/inspection. Then wire explicit simulation commands and reciprocal pairing. Add nursery proposal/admission only after candidate semantics converge; finally wire child Run and recovery. Existing `creation.js` is a behavioral reference, not a module to invoke wholesale: its automatic initial build, global single specimen and execution-in-copy path do not fit ranch admission.

Rendering thirty-two bodies at the existing high-resolution portrait quality is unjustified. Use one shared meadow canvas, cached compiled residents, stable positions, visible-only painting and an explicit global geometry budget; the selected portrait gets detail separately. Role ownership must remain valid under any reduced detail. Measure maximum population, dense pairings and mobile viewport before selecting frame rate; publish observed metrics with environment rather than promise 60 fps. View schedules must not affect deterministic world replay. Bound activity storage and report dropped informational events.

Before implementation, settle the first reports' open choices: semantics permits some protected effectful recipients while genetics initially restricts mating/merge to pure parents; lineage is companion-only in one proposal and partly embedded genetics in another. Recommend a pure-parent task pilot and separate companion lineage for the first website, with source-authored resolved body traits. UI eligibility and recovery promises must track the audited final decision, not implement both inconsistent variants.

The ten reports should converge into one concrete candidate specifying command names, stores, schemas, eligibility, identity projections and these screen states. Then obtain the requested nine independent audits with actual routes/results recorded before implementation. Experience audit criteria: all residents accessible without canvas; actual reciprocal protocol; zero implicit child/run; clear recipe-specific changes; missing metadata never fabricated; rejected and stale candidates intelligible; independent Run produces a useful child result; exact copy distinguished; mobile/reduced-motion complete; finite resources surfaced.

Suggested browser acceptance scenarios: instrument execution during first load, inspection, simulation, preparation, admission and recovery and expect zero until explicit Run; keyboard-complete the pair-to-child flow; inspect two identical-source residents independently; reject unit mismatch and stale parents without state corruption; admit one child and see empty results until Run; pause/step with reduced motion; verify hidden-tab resume does not catch up; exercise full nursery/spawn capacity; recover source without companions and see missing thought/type/lineage labels. These are required tests for the future candidate, not checks completed by this report.
